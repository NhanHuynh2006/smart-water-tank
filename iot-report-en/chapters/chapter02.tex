\chapter{SYSTEM ARCHITECTURE, HARDWARE AND PROTOCOL}
\label{chap:arch}

\section{Overall architecture}
\label{sec:o3-1}

The system consists of four blocks in series: an edge node built around an ESP32 with its sensors and one actuator; an MQTT broker acting as a content based message router; a backend service comprising an ingestion process, a database and an API server; and a web dashboard. A fifth, optional element is an outbound tunnel that publishes the dashboard on a public HTTPS address so that the tank can be supervised from anywhere with Internet access, not only from inside the laboratory network.

\begin{figure}[H]
    \centering
    \resizebox{\textwidth}{!}{\input{fig/architecture.tex}}
    \caption{Architecture of the smart water tank system. The closed control loop lives entirely inside the edge node.}
    \label{fig:kientruc}
\end{figure}

Mapping onto the five layer model of Section~\ref{sec:o2-2}: the perception layer is the ESP32 with its sensors and relay; the transport layer is a Mosquitto broker over Wi-Fi; the processing layer is the ingestion process, SQLite and a FastAPI server; the application layer is the dashboard; and the business layer, kept deliberately minimal at this scale, is the daily volume report. The single most important property of Figure \ref{fig:kientruc} is that the closed control loop lives entirely inside the first block, so the remaining blocks never sit on the path of a pump switching decision.

Wi-Fi was selected over BLE, Zigbee and LoRaWAN for three reasons. The system is mains powered, so the low energy advantage of BLE and LoRaWAN carries no weight. The device sits indoors within a few tens of metres, comfortably inside Wi-Fi coverage. Most importantly, Wi-Fi gives the node a native IP address so it speaks to the broker directly, whereas every alternative needs an edge gateway to translate between two protocol worlds \cite{slide02}, adding hardware and a point of failure. The conclusion reverses for tanks spread over a wide area or for a battery powered node. One practical constraint surfaced on the bench: the ESP32 radio supports only the 2.4 GHz band, so the node cannot join a 5 GHz only access point, and the firmware therefore accepts up to three network credentials and tries them in turn.

\section{Function placement and edge autonomy}
\label{sec:o3-2}

This is the central architectural decision of the project. The assignment requires that level control keep working during a network outage. Combined with the placement rule of Section~\ref{sec:o2-2}, which states that any operation needing an immediate safe stop must be computed at the edge \cite{slide01}, the group adopted a single principle: \textbf{the server never issues a direct pump switching command in automatic mode, and never bypasses the device's own checks in manual mode.}

The edge node therefore owns sensor reading and filtering, the control state machine, every safety interlock, all fault detection rules, the pump health classifier and volume accumulation, because each of these demands a deterministic cycle and has to survive an outage. The backend owns only the things the node cannot do well: durable history, the daily volume report, and statistical baseline leak detection, which needs a window of several days and exceeds the memory available on the microcontroller.

This split makes the system degrade in a controlled way when connectivity is lost: the user loses remote visibility and remote commands, but the tank is still refilled at the correct thresholds and every safety constraint is still enforced. The behaviour is verified experimentally in Section~\ref{sec:o8-5}.

\textbf{The tank.} The storage tank has a square base of 10 by 10 centimetres, so one centimetre of level is exactly 0.1 litres. The transducer face sits 15.88 centimetres above the floor, measured with a ruler as six and a quarter inches. The working range is the lowest 12.4 centimetres, which the firmware treats as 100 percent, giving a usable volume of 1.24 litres and leaving 3.5 centimetres of air below the sensor at a full tank, outside its minimum range. The small volume is deliberate: it makes a full fill and drain cycle last a few minutes, so many control cycles can be observed in one bench session.

\textbf{Level sensing.} Non contact ultrasonic measurement was chosen because the transducer never touches the water, so it neither corrodes nor accumulates deposits, and its output does not depend on water conductivity. Two properties of this particular installation shaped the software in Chapter \ref{chap:control}. First, the beam of an HC-SR04 spreads over roughly 15 degrees and is already about 8 centimetres wide when it reaches the water, against a 10 centimetre tank, so the edge of the beam strikes the wall on every ping and a fraction of echoes return from the wall or the floor rather than the surface. Second, the sensor occasionally locks up after a supply disturbance and stays silent until its supply is cycled, which no firmware reset can reach. The first property is handled by a robust filter; the second by a timeout rule and a documented recovery procedure. The calibration of Section~\ref{sec:o8-2} found a third property: when the water surface is 7.9 to 8.7 centimetres below the transducer, that is at a level of about 7.2 to 8.0 centimetres or 58 to 64 percent, the sensor does not return the surface at all but a stable stray echo, reading 1.0 centimetre or a distance beyond the floor in every one of forty pings. Because the stray value is steady it cannot be filtered out as noise; Section~\ref{sec:o6-2} explains how the firmware crosses this band on its model.

\textbf{Echo line.} The echo line was first routed through a TXS0108E automatic direction level translator. That part is designed for open drain buses and its internal pull ups and edge accelerators distorted the echo pulse, whose width is the only carrier of information. Replacing it with a plain 10 k$\Omega$ and 20 k$\Omega$ divider removed a 28 to 30 percent echo loss, as recorded in Appendix \ref{app:bench}.

\textbf{Flow sensing.} Both inlet and outlet carry a YF-S401 turbine sensor, where pulse frequency relates to flow as $Q = f/K$. Because the assignment makes the flow sensor mandatory, the group states its status precisely rather than simply as met: the hardware requirement is implemented, the measurement path is only partly validated, and control and accounting use flow derived from the level.

The history explains why. Until 22 September both signal lines carried about 1500 hertz of interference while the pump ran, forty times the real pulse rate, and a flyback diode and physical separation of the wiring did not reduce it (Section~\ref{sec:o8-2}). The firmware was therefore given two sources of flow, selected at compile time: the pulse counters, or flow derived from the level rate described in Section~\ref{sec:o6-2}. The prototype runs with the second. On 5 October the power stage was rewired: the relay now switches the supply ahead of the current sensor and the pump, the pump leads carry a diode and a capacitor at the motor, a 470 microfarad capacitor sits on the controller board, and the sensor lines were rerouted. The firmware also ignores any edge that arrives less than 1.2 milliseconds after the previous one, a pulse width filter that rejects spikes while passing the real pulses, which are about 30 milliseconds apart at these flows. After that change the inlet sensor reads 0 hertz with the pump off and 20 to 30 hertz with it running, which is water rather than interference. Its factor was calibrated against the ruler and the tank geometry, $K = 85.5$ pulses per second per litre per minute instead of the nominal 98, and its reading is now published as \texttt{sens\_in\_lpm} and drives the level model of Section~\ref{sec:o6-2}. The outlet sensor remains of limited use: the bench drain of 0.1 to 0.2 litres per minute is below the 0.3 litre per minute starting flow of the YF-S401, so it turns only intermittently.

\textbf{Float switches.} The two floats are not there to measure level. The upper float forms an overflow guard that operates independently of the ultrasonic path, and the lower float gives the pump a second, independent permission to start when the tank is low. Because two independent sources exist, the firmware can detect a contradiction between them and conclude that one reading is wrong. This is how the system satisfies the requirement to handle implausible sensor readings, as detailed in Section~\ref{sec:o6-4}. Float polarity was measured rather than assumed, because a float wired with the opposite sense reads as permanently engaged.

\textbf{Current sensing.} The ACS712 output passes through a one to one divider that moves its no load point from 2.5 volts to 1.25 volts, the middle of the converter span. The 5 ampere variant produces 185 millivolts per ampere, which becomes 92.5 millivolts per ampere at the pin, or 10.81 milliamperes per millivolt. The firmware subtracts a startup offset averaged over 200 samples, reports the result in milliamperes, and reports zero below a 4 millivolt noise floor, since with the pump off the raw reading wanders between 0 and 2.7 millivolts, a single converter step being 0.8 millivolts. The measurement cannot resolve currents below about 40 milliamperes, which is enough to separate a running pump from a stopped one but not to characterise the motor, and Section~\ref{sec:o8-7} returns to this.

\section{Power stage, supply and mechanical build}
\label{sec:o3-4}

The pump is switched through a relay module. A power MOSFET was considered, since the lectures favour it in edge designs of modest power thanks to its very low on resistance \cite{slide01}, but the relay was chosen because a pump running in two states at a low switching rate never exercises the frequency advantage of a MOSFET, and because the module drives the load from its own supply. Inductive protection uses a 1N4007 diode antiparallel across the pump terminals, alongside a 100 nF ceramic capacitor at the motor terminals whose purpose is not spike suppression but damping of brush noise. The relay polarity was determined by measurement: the module fitted is active high, and an earlier configuration that assumed active low made every stop command start the pump, as recorded in Appendix \ref{app:bench}. The relay control pin is driven to the off level as the very first statement of the firmware, before the serial port or any sensor is initialised. The relay input moved to GPIO 10 on 5 October. That pin is wired to the flash chip on most ESP32 modules and is free only when the flash runs in dual line (DIO) mode, so the build sets \texttt{board\_build.flash\_mode = dio}; the group confirmed on the bench that the pin then switches the relay without resetting the chip.

The system runs from a 12 volt supply through a 2 ampere fuse and a 5 volt, 5 ampere buck converter shared by the pump and the logic. Because the rail is shared, distribution matters: every load branch leaves the converter output terminal in a star, and the pump ground does not share a conductor with the controller ground. A 470 microfarad capacitor on the controller board buffers the inrush current of the motor, whose start peak would otherwise pull the rail below the brownout threshold and reset the chip \cite{slide01}.

\section{Design principles and topic tree}
\label{sec:o4-1}

Three principles govern the protocol specification. First, every message carries a device generated timestamp, because although TCP preserves ordering on a single socket, brokers process multiple threads concurrently so final arrival order may differ, and deterministic ordering must therefore be imposed at application level inside the payload itself \cite{slide03}. Second, the quality of service level is chosen per topic according to the consequence of losing a message. Third, every downward command must be answered by an upward acknowledgement carrying the same identifier.

The topic root is built from broad scope down to the individual device as \texttt{wt/lab1/esp32-01}, following the hierarchical naming rule given in the lectures \cite{slide03}.

\caption{MQTT topic tree and the reasoning behind each setting.}

\centering

\begin{tabular}{|p{2.8cm}|p{0.8cm}|p{1.3cm}|p{7.5cm}|}
\hline
\textbf{Topic} & \textbf{QoS} & \textbf{Retain} & \textbf{Reasoning} \\
\hline
\texttt{.../telemetry} & 0 & No & One lost sample in a continuous 1 Hz stream changes no conclusion about the trend, and in exchange latency is lowest with no device buffer \\
\hline
\texttt{.../state/pump} & 1 & Yes & Published only on change, so a loss leaves the dashboard wrong until the next transition \\
\hline
\texttt{.../event/fault} & 1 & No & Losing an alarm is incorrect behaviour for a safety function \\
\hline
\texttt{.../status} & 1 & Yes & The last will payload is published once, with no retransmission \\
\hline
\texttt{.../cmd} and \texttt{.../cmd/ack} & 1 & No & A lost command or acknowledgement is a direct functional failure \\
\hline
\end{tabular}
\end{table}

The design respects all three naming pitfalls listed in the lectures \cite{slide03}: no leading separator, no whitespace inside the path, and six explicit subscriptions rather than a root wildcard. No topic uses the highest quality of service level, because it requires a four step handshake and packet identifier tracking on the edge device, while the duplicate delivery problem it solves is already handled at application level: each command carries a unique identifier, so a duplicate simply causes the device to resend the same acknowledgement without acting twice. This is the idempotency property of Section~\ref{sec:o2-5}.

\section{Message structure and fault codes}
\label{sec:o4-2}

Payloads use JSON built with a statically allocated document, following the rule that forbids dynamic allocation inside the loop \cite{slide05, arduinojson}.

\begin{lstlisting}[caption={Telemetry message payload, abridged.},label={lst:telemetry}]
{ "dev":"esp32-01", "ts":1790160600, "ts_ms":1790160600123, "seq":10421,
  "level_pct":62.4, "level_cm":7.74, "level_ok":true,
  "level_rate_cms":0.036, "level_model_cm":7.71, "blind_ms":0,
  "flow_lpm":0.36, "volume_l":143.62, "volume_today_l":12.40,
  "flow_out_lpm":0.16, "volume_out_l":98.10, "flow_src":"level",
  "sens_in_lpm":0.35, "sens_out_lpm":0.00, "sens_in_l":21.80,
  "pump":true, "state":"FILLING", "mode":"AUTO",
  "current_mv":36.1, "current_ma":390.2, "pump_health":"ok",
  "float_max":false, "float_min":false, "fault":"", "rssi":-55,
  "lv_try":605, "lv_ok":563, "rj_spread":31, "ctl_gap_ms":201 }
\end{lstlisting}

The \texttt{seq} field is a monotonically increasing counter allowing lost messages to be counted exactly in Section~\ref{sec:o8-5}. The \texttt{ts\_ms} field is produced by the device after time synchronisation and supports latency measurement. The \texttt{level\_ok} field states whether the reading can be trusted, letting the interface distinguish a genuinely low tank from a broken sensor. The \texttt{flow\_src} field states whether the flow figures come from the pulse sensors or are derived from the level, so no consumer can mistake one for the other. The \texttt{sens\_*} fields carry the turbine readings alongside, so the two estimates can be compared in the stored data. The \texttt{lv\_try}, \texttt{lv\_ok} and \texttt{rj\_*} counters record how many level pings were attempted, accepted and rejected at each filter stage; they turned out to be the most useful diagnostic in the project, as Appendix \ref{app:bench} shows. The \texttt{ctl\_gap\_ms} field reports the longest control period since the previous live message, so the first message after an outage proves whether the control loop was ever stalled by the network. Messages replayed after reconnection carry a \texttt{replay} flag and a reduced field set, and are excluded from latency statistics. The full message runs to several hundred bytes, so the serialisation buffer is 1024 bytes and the MQTT client buffer 1200 bytes; Appendix \ref{app:bench} explains why both margins are explicit.

Eleven fault codes are generated on the device and one on the backend. They fall into three groups. The self clearing group, \texttt{SENSOR\_TIMEOUT}, \texttt{SENSOR\_CONFLICT} and \texttt{LEVEL\_LOST}, concerns signal quality and resolves on its own once the signal has been valid for long enough. The latching group, \texttt{OVERFLOW}, \texttt{NO\_CURRENT}, \texttt{DRY\_RUN}, \texttt{NO\_PROGRESS}, \texttt{FILL\_TIMEOUT}, \texttt{HARD\_LIMIT} and \texttt{VOLUME\_LIMIT}, requires the operator to confirm that the physical cause has been dealt with before the fault can be cleared. The warning group, \texttt{LEAK\_SUSPECTED} on the device and \texttt{LEAK\_BASELINE} on the backend, raises an alert without locking the pump. Every fault message also carries the pump health label and the pump current at the instant of the fault, captured before the pump is stopped, so the record states not only that something failed but which side of the pump failed. Trigger conditions are given in Section~\ref{sec:o6-4}.

\section{Command and acknowledgement mechanism}
\label{sec:o4-3}

This section implements the feedback sync principle of Section~\ref{sec:o2-5} and satisfies the requirement that commands be acknowledged with a verified state.

\begin{lstlisting}[caption={Command message and matching acknowledgement.},label={lst:cmd}]
// .../cmd
{"cmd_id":"a7f3c2e1","action":"pump","value":true,"ts":1735689600}
// .../cmd/ack
{"dev":"esp32-01","cmd_id":"a7f3c2e1","status":"rejected",
 "reason":"overflow_guard","state":"OVERFLOW_LOCK","pump":false}
\end{lstlisting}

The acknowledgement reports not only the outcome but also the actual device state after processing, so the dashboard always displays a state the device has confirmed rather than one the user has just requested. Four actions are supported: change mode, switch the pump, clear a fault and reset the volume counters. Ten rejection reasons are defined: \texttt{auto\_mode\_active}, \texttt{fault\_active}, \texttt{overflow\_guard}, \texttt{float\_max\_triggered}, \texttt{water\_too\_close}, \texttt{level\_sensor\_invalid}, \texttt{min\_off\_time}, \texttt{no\_active\_fault}, \texttt{condition\_still\_present} and \texttt{unknown\_action}. The dashboard translates each into a plain sentence, and for \texttt{min\_off\_time} it shows a countdown on the pump button until a start will be accepted.

The rejection table is worth more than a debugging aid: during the demonstration, pressing the pump on button while a fault is active and seeing an explicit rejection with a named reason is visible proof that manual mode cannot override the interlocks.

\section{Connection lifecycle and availability monitoring}
\label{sec:o4-4}

The firmware implements the four state connection machine described in the lectures. The critical point is the accompanying design note: connection logic must never sit inside a blocking wait loop, because that stalls the processor and suspends both analog sampling and safety checks for the whole outage \cite{slide03}. Our reconnection routine therefore never blocks, retries only once its interval has elapsed, and the control loop runs independently of network state. The retry interval grows exponentially with an upper bound, $T_{retry} = \min(T_{max}, T_{base} \cdot 2^{n})$ with $T_{base}$ of 1 second and $T_{max}$ of 30 seconds \cite{slide06}.

A non blocking design still has to account for the calls it cannot avoid. Opening a TCP connection to an unreachable broker blocks inside the network stack, and the default timeout of the ESP32 client is three seconds, during which the control loop does not run. The firmware therefore opens the socket itself with a 500 millisecond limit before handing it to the MQTT client, and bounds the wait for the broker's connection acknowledgement to two seconds. Two further bounds came from the outage test of Section~\ref{sec:o8-5}. Writing to a socket whose peer has silently vanished blocks until the transmit buffer drains, which in the first firmware stalled the control loop for up to ten seconds; the firmware now checks, without waiting, whether the socket can accept data before every publish, and closes it once it has refused data for three seconds, so the ring buffer of Section~\ref{sec:o7-3} takes over after about three seconds instead of after the 15 second keep alive. And a new Wi-Fi association is attempted at most once every ten seconds, because restarting it every second, as an earlier version did, never left the radio enough time to finish joining. After a Wi-Fi reconnection the device also resolves the broker's host name over multicast DNS, because a laptop that moves between networks receives a different address on each; a fixed fallback address is used if the name does not resolve.

On connecting, the device pre registers a last will message announcing that it is offline, then overwrites it with an online message once the session is established. Should the node suffer an abrupt loss of power, the broker keep alive supervisor publishes the stored will by itself \cite{slide03}, so the interface switches to a disconnected state with no polling logic on the application side. A second backend check treats the device as offline when the newest telemetry message is older than 5 seconds. The two complement each other, since the will reacts quickly to a total power loss while the freshness check also catches a live session whose data stream has stopped.
